# RS485 半雙工 DE 控制 — 驗證清單

> **用途**：驗證 RS485 半雙工的 DE（方向腳）控制方案——`uart_drv.py` 1ms 純 Python 版 vs `rs485_hd` C 模組全自動版——的**穩定性與延遲**，定出可上生產的配置。
> **最後更新**：2026-08-21
> **相關文件**：`doc/03_notes/04_rs485_de_timing.md`（調查與已實作結果）、`ext_mod/mp_rs485_hd/`、`slave/driver/uart_drv.py`、`test/protocol/rs485_de_scan.py`

---

## 測試目標

1. **確認 `rs485_hd` 全自動 DE 可用**：`rs485_hd.enable(1, de=7)` 後 `uart.write()` 是否真的「硬體自動控 DE、寫完就走、回覆正確」。
2. **量出三種方案的真實延遲與成功率**（同樣的 ping-pong 測試）：
   - A. 純 Python `Pin.value()` + `sleep_ms(1)` + `txdone()`（`uart_drv.py` 現況）
   - B. `rs485_hd` C 模組全自動（硬體控 DE，0 管理）
   - 對照組：0ms settle（已知不穩，當作「不能用的下界」）
3. **判定哪種方案上生產**：穩定性 100% + 延遲最低 + 維護成本最低。

## 已完成（實測通過，2026-08-21 夜）

- [x] **純 Python 1ms settle：ping-pong 100% 穩定**（sender 1ms / 2ms / 3ms 各 25~50 輪全過；0ms 漂移 0%~100%）

## 已知問題 / 待決

- [ ] **rs485_hd 的 `uart_set_rx_timeout(10)` 是猜的**：RS485 模式需要「幀結束」判斷來清回波，10（baud 週期）約 1 byte 時間。若回波污染或幀被切，需調這個值
- [ ] **rs485_hd 只在 ESP32 系有效**（ESP-IDF 才有 RS485 模式）；RP2040 等無此 API，用回 `uart_drv.py` 純 Python 版
- [ ] **1401 為何 esptool 連不上**（REPL 通、download mode 進不去）——疑似板子 USB-JTAG 需要實體 BOOT 按鍵，重刷時一併確認
- [ ] **build 自動 flash 會亂選 port**：之後編譯請手動指定 `--port`，避免再寫錯板子

## 筆記

- **跨 chunk 組幀是必要的**：9600 baud 下 `uart.any()` 把一幀拆成多段（如 `AA` / `00 55 55` / `55 BB`），單一 chunk 找不到完整幀。測試接收端必須累積緩衝 + `find(0xAA)` 掃描（參考 `circuit_bus_*.py` 的 `_Assembler`）。
- **self-echo 干擾**：發送時自己的 RO 也開著（DE=1），會收到自己發的幀。計數時要過濾「發送後 ~30ms 內到達」的資料，只認對端 echo。
- **延遲數據參考**（6B 幀 @9600）：純傳輸 6.25ms；純 Python 1ms 版 ≈ 7.5ms；rs485_hd 應 ≈ 6.3ms（省掉 settle）。
- REPL 連板子：pyserial 直接開 `/dev/cu.usbmodemXXX`，**先 Ctrl-B 出 raw REPL 再 Ctrl-C 中斷**，`dtr=rts=False` 避免誤觸重置。
