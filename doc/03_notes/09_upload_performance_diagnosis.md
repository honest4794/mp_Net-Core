# 上傳效能診斷報告（為什麼停在 70KB/s）

> **用途**：記錄「NetBusMaster 上傳 4KB 幀明明解碼/寫入都 MB 級，實際卻只有 70KB/s」的完整診斷過程與結論。接手同事讀這份就能理解「慢在哪、為什麼、哪些數字可信」。
> **分類**：筆記（03_notes）
> **最後更新**：2026-08-27
> **相關文件**：`10_upload_performance_changes.md`（改動清單與回滾）、`08_performance_benchmark.md`（前次性能基準）
> **測試工具**：`test/protocol/` 目錄下的 probe_* / upload_* / measure_fix / overnight_test 等腳本

## 0. 一分鐘結論

| 問題 | 結論 |
|---|---|
| 為什麼 4KB 解碼/寫入都 MB 級，上傳卻 70KB/s？ | **不是複製、不是解碼、不是寫入、不是網路**，是 **stop-and-wait（停等協議）+ 1KB chunk**。每發 1 包就要等一個 ACK 才發下一包，吞吐 = chunk_size ÷ 每包往返延遲 |
| 每包往返延遲是多少？ | ~15ms（不是 3.5ms 的網路 ping；網路只佔其中一小部分） |
| 70KB/s 怎麼來的？ | 1024B ÷ 15ms ≈ 68KB/s，與實測完全吻合 |
| 網路快嗎？ | 快。ICMP ping 3.5ms，前次文件裸 TCP 上載 9.35MB/s 都是真的 |
| 那 15ms 花在哪？ | 排程延遲（core0 上 standby task 擠壓 network 輪詢）+ 寫檔 + 一個 4 位元組的 recv 緩衝 bug |
| 真正的天花板？ | 停等協議本身。只要「發一包等一個 ACK」，吞吐就被 15ms 鎖死；要上 MB 級必須改滑動視窗 |

> ⚠️ 一句話：**網路往返和「停等協議每包延遲」是兩件事**。之前我把它們混為一談，敘述有誤，本文件已修正。

## 1. 實測數據全表

### 1.1 各環節「單一方向」的能力（都不是瓶頸）

| 環節 | 數字 | 來源 |
|---|---|---|
| 網路 ping | 3.5ms | `ping 10.10.1.26` |
| 解碼（StreamParser pop_frame） | 1K=3.9 / 4K=12 / 8K=16.2 MB/s | `probe_reply_path.py` |
| 寫入（緩衝，不 flush） | 1K=0.7 / 4K=1.9 / 8K=2.3 / 16K=3.0 MB/s | `probe_flush.py` |
| 寫入（每包 flush，真實落盤） | 4K=1179 KB/s（3390µs/包） | `probe_flush.py` |
| statvfs | 138µs（可忽略） | `probe_flush.py` |

### 1.2 收→解碼→回 ACK 這條路徑（每包 4KB）

| 環節 | 耗時 |
|---|---|
| StreamParser 拆幀（含 CRC） | 431µs |
| SchemaCodec.decode（viper 預編譯） | 218µs |
| SchemaCodec.encode + Proto.pack（組 ACK） | 201µs |
| **整條收→解→回（合計）** | **740µs** |

> 關鍵：回覆路徑的「解碼」早已是 `@micropython.viper` 原生碼，不是每次慢慢重新解碼。740µs 只佔每包 15ms 的 5%，**不是瓶頸**。所以「預先編譯」方向不成立——它早就編譯過了。

### 1.3 停等吞吐 vs chunk 大小（線性 = 停等鐵證）

| chunk | 實測吞吐 |
|---|---|
| 1KB | 62.4 KB/s |
| 2KB | 113.9 KB/s |
| 4KB | 237.5 KB/s |

吞吐 ∝ chunk 大小，比例固定 → 每包卡在固定 ~15ms。`1024B ÷ 15ms ≈ 68KB/s` 就是你看到的 70KB/s。

### 1.4 滑動視窗（移除停等後的真正天花板）

| 視窗 | 吞吐（4KB chunk） |
|---|---|
| 1（=停等） | 194 KB/s |
| 2 | 324 KB/s |
| 4 | 502 KB/s |
| 8 | 522 KB/s |
| 16 | 496 KB/s |

視窗 4~8 到 ~520KB/s 就飽和，**再大不漲**。這是停等被拿掉後的下一個天花板。

### 1.5 排程成本（standby task 空轉實測）

core0 每輪把 7 個 task 全部呼叫一次，每秒 409 輪。實測各 task：

| task | 每秒被呼叫 | 真正做事 | 空轉率 |
|---|---|---|---|
| network | 409 | 409 | 0% |
| render | 409 | 50 | 88% |
| now / web_ui / circuit / bus_decode / log | 各 409 | 0 | **100%** |
| hw_sample（core1） | 1614 | 0 | 100% |

> 5 個 task 100% 空轉卻仍被每輪呼叫 → 擠壓 network 兩次被服務之間的間隔 → 拉長每包 RTT。

## 2. 一個具體 bug：recv 緩衝少 4 位元組

4KB chunk 的完整 WebSocket 幀 = **4119 bytes**（4115 NC4 幀 + 4 位元組 WS 頭），但 slave 的 recv 緩衝 = `RX_BUF_SIZE = 4115` 位元組。

結果：每一包都被 TCP 拆成「4115 + 4」兩段，slave 第一次 `recv_into` 只拿到 4115（差 4 位元組組不成完整幀），要等下一輪 poll 再收那 4 位元組才能解碼。

修法：recv 緩衝改 `RX_BUF_SIZE + 8`（slot 大小不變，只讓 recv 能一次裝下完整 WS 幀）。

實測：修完後 CHUNK_ACK RTT 16.87ms → 15.11ms，停等吞吐 230 → 254 KB/s。**這是真實 bug、值得修，但不是 70KB/s 的主因**。

---

## 3. 每包 15ms 的組成（修正後的誠實版）

```
每包停等往返 ~15ms ≈
  網路來回 ~3.5ms（ping）
+ 排程延遲（network 等 core0 輪到，受 standby task 擠壓）
+ 寫檔 flush ~3.4ms（4KB 每包落盤）
+ recv 拆包多等一輪（bug 已修）
```

之前把這 15ms 全部歸給「網路」是錯的。網路只佔 3.5ms；剩下是排程 + 寫檔 + 拆包。

## 4. 結論與出路

| 結論 | 說明 |
|---|---|
| 停等協議是主因 | 只要「發一包等一個 ACK」，吞吐 = chunk/15ms，永遠上不去 |
| chunk 加大只能救部分 | 1KB→4KB 已把 70→240KB/s（且 4KB 是 `RX_BUF_SIZE` 一幀一槽的極限） |
| 真正出路 = 滑動視窗 | 連發 4~8 包再等 ACK，實測到 ~520KB/s |
| 下一道牆（520KB/s 之後） | 不是網路/解碼/寫入，是「每包固定延遲」仍存在；要再上得改 slave 端批量化寫入或更深排程改造 |

> 你之前測到「4KB 來回 4MB/s」是**管道化**吞吐，不是停等吞吐。兩者量綱不同，之前我沒講清楚，特此更正。
