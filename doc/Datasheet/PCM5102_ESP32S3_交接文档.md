# ESP32-S3 + PCM5102 音频播放 交接文档

> 目标：用 MicroPython 驱动 ESP32-S3 的 I2S 外设，将测试音效输出到 PCM5102 DAC，从耳机/功放听到声音。
> 状态：✅ **已跑通有声音**（2026-08-30 验证）

---

## 1. 硬件清单

| 部件 | 说明 |
|---|---|
| ESP32-S3 开发板 | 固件：MicroPython v1.26.1（ESP32_GENERIC_S3-SPIRAM_OCT，带 Octal SPIRAM）|
| PCM5102 模块 | I2S DAC，约 2Vrms line-out |
| 耳机 / 功放 | 接 DAC 的 LOUT / ROUT（line-out 不能直推无源小喇叭）|

板子通过 USB 连接 Mac，串口节点：**`/dev/cu.usbmodem1101`**
（设备 VID 0x303A / PID 0x4001，是 ESP32-S3 内置 USB Serial/JTAG，**不是 USB 声卡**）

## 2. 接线（关键！）

| ESP32-S3 GPIO | PCM5102 脚 | 类型 | 说明 |
|---|---|---|---|
| GPIO 9 | **BCK** | I2S 数据时钟 | 必须接 GPIO，由 I2S 外设驱动 |
| GPIO 10 | **DIN** | I2S 数据 | 必须接 GPIO |
| GPIO 11 | **LCK** | 左右声道时钟 WS | 必须接 GPIO |
| GPIO 12 | **XSMT** | 静音控制 | 高=出声，低=静音。**接 GPIO 由软件控制解除静音** |
| — | SCK | 固定 | **接 GND**（强制内部 PLL 从 BCK 恢复主时钟）|
| — | FMT | 固定 | **接 GND**（I2S 格式）|
| — | VIN | 电源 | 3.3V ~ 5V |
| — | GND | 地 | **必须与 ESP32-S3 共地**，否则完全无声 |

### 三条命脉（无声时先查这三条）
1. **XSMT 必须拉高** —— 悬空=静音，这是本项目无声的**主因**
2. **SCK 接 GND** —— 比悬空稳（悬空电平不定，PLL 可能不工作）
3. **共地** —— ESP32 与 DAC 的 GND 必须相连

```bash
python3 -m mpremote connect /dev/cu.usbmodem1101 ls
python3 -m mpremote connect /dev/cu.usbmodem1101 repl
```

## 4. 软件脚本

位于 `/Users/user/Documents/code/git/temp/`，全部已实测：

### `pcm5102_play.py` —— 主播放脚本（已写入板子 flash）
- 功能：静音预热 → 880Hz 双哔 → 200→2000Hz 扫频 → 440Hz 长音（共约 3.6s）
- 关键点：
  - `machine.I2S(0, sck=9, ws=11, sd=10, mode=I2S.TX, bits=16, format=I2S.STEREO, rate=44100, ibuf=40000)`
  - **先 `Pin(12, Pin.OUT).value(1)` 拉高 XSMT 解除静音，再启动 I2S**
  - 用 `struct.pack("<h", v)` 生成 16bit PCM（MicroPython 的 `to_bytes` 不支持关键字参数！）

### `i2s_track_test.py` —— 音轨逐一播放 + 合成测试（✅ 已跑通）
- 功能：音轨1(A4) → 音轨2(C#5) → 音轨3(E5) 各自单独播 0.8s，最后三轨一起合成播 1.6s
- 关键点：
  - **wavetable 查表法**：预生成 256 点正弦表，相位用定点整数累加（高 8 位查表），
    生成时零 `math.sin` 调用
  - **实测"计算资源很花时间吗"**（纯 Python 生成耗时，非播放耗时）：
    - 单音轨 0.8s 音频 ≈ **0.85~1.0s** → 生成接近实时
    - 三轨合成 1.6s 音频 ≈ **4.8s** → 3 轨叠加慢 3 倍，纯 Python 循环是瓶颈
- 结论：纯 Python 生成 1:1 都吃力，3 轨合成更慢 → 需要优化（见下）

### `i2s_stream_test.py` —— 音轨测试·优化版（✅ 已跑通，推荐用这个）
- 功能：同上一版（1→2→3→一起播），但改为 **viper 原生加速 + 分块流式**
- 优化手段（回答"非阻塞/不花时间"）：
  - **`@micropython.viper` 原生代码**：关键循环编译成机器码，比纯 Python 快约 5~20 倍
  - **定点整数运算**：音量 0.3 / 限幅 0.8 都转成 16.15 定点（`int(0.3*32768)`），
    避免浮点除法；相位用 16.8 定点（高 8 位查表）
  - **分块流式**：一次只生成 2048 样本（≈46ms）立刻 `write()`，边算边播，
    生成与播放由 DMA 缓冲重叠 → 播放不被计算拖慢，内存占用也小
  - **复用缓冲**：PCM 缓冲 `array('h')` 和相位 `array('i')` 只分配一次
- **实测对比**（同板同环境）：
  | 版本 | 单音轨 0.8s 音频 | 三轨合成 1.6s 音频 |
  |---|---|---|
  | 纯 Python 预生成 | 0.85~1.0s 生成 | 4.8s 生成 |
  | viper 流式 | **0.801s 边算边播** | **1.602s 边算边播** |
- 结论：viper 流式把 3 轨合成从 4.8s 压到 1.6s（≈3 倍，正好≈实时播放时长），
  CPU 不再是瓶颈；真实项目（几十轨、实时合成、MIDI）用这套：viper + 查表 + 流式分块

### `i2s_bench.py` —— 合成性能 benchmark（✅ 已跑通，回答"能合成多少轨"）
- 功能：viper 生成 1s 音频，测 1/2/4/8/16/32/64/96 轨纯 CPU 耗时
- 实测（ESP32-S3 单核、MicroPython v1.26.1、44.1kHz、viper+查表+定点）：
  | 轨数 | 1 | 2 | 4 | 8 | 16 | 32 | 64 | 96 |
  |---|---|---|---|---|---|---|---|---|
  | 耗时 ms | 38 | 54 | 87 | 151 | 281 | 539 | 1057 | 1575 |
- 关键结论：
  - **不是慢一倍，是线性增长**：每加一轨固定 +16ms（N×每轨成本）
  - **viper 单核实时上限 ≈ 40 轨**（64 轨 1057ms 超实时，32 轨仅 54% CPU）
  - 对比纯 Python：单轨生成 0.8s 就要 ~0.9s，2 轨即超时；viper 快约 50 倍

### `i2s_dualcore.py` —— 双核流水线测试（✅ 已跑通，生产者/消费者）
- 功能：生产者线程(viper 合成 96 或 40 轨) → 乒乓双缓冲 → 主线程(I2S 播放)
- 实测：
  - **96 轨**（单核 1.57s/s 已超时）：播放 4s 音频耗时 **6.1s（超时 53%）**，
    生产总生成 6.07s ≈ 播放耗时 → **GIL 限制：总生成算力仍是单核**，96 轨本就超单核能力
  - **40 轨**（单核能力内）：播放 4s 音频耗时 **3.97s（实时✅）**，生产总生成 2.58s
    → 流水线重叠有效（write 阻塞期间生产线程在跑，占播放 64%）
- 关键结论：
  - **MicroPython 线程有 GIL**，两线程不能同时执行 Python 代码，
    I2S.write() 阻塞时是否释放 GIL 决定重叠效果
  - 双核流水线**不能突破 GIL 的单核上限**（96 轨仍超时），
    但在单核能力内能**消除生成开销对播放的干扰**（40 轨流畅实时）
  - 要真正用双核并行：必须用 ESP-IDF(C 语言) 或 CircuitPython
    （CircuitPython 无 GIL，且 I2S DMA 后台播放自动并行）——
    本项目 MicroPython 方案下，**上限 ≈ 40 轨实时合成**

### `i2s_clip_test.py` —— 防削波对比测试（✅ 已跑通）
- 功能：同一组三音和弦，三种音量/限幅处理，亲耳对比"爆声"从哪来、怎么解决
- 听感对比：
  1. **硬截断版**（每轨 0.5，叠加峰值 1.5）：超出 16bit 范围直接砍 → 明显爆/破声
  2. **预缩放版**（每轨 1/3）：峰值正好 1.0 → 干净但整体偏小声
  3. **软限幅版**（每轨 0.5 + limit=0.8）：超出阈值平滑压缩 → 响且不爆（推荐）
- 关键知识点：
  - **爆声原理**：多个声音相加后数值超出 ±32767，硬截断让波形顶部变平 → 产生大量高次谐波 → 破音
  - **手段 1 预缩放**：每轨音量 1/N（N=音轨数），最安全但浪费动态范围
  - **手段 2 软限幅**：`|v|<=limit 线性, 超出部分压缩`（分段线性 soft-clip），
    既响又不爆，是合成器/混音器通用做法；类似还有 tanh 软削波（更暖但更慢）
  - 实用建议：每轨设 0.3~0.5，混音后加一层软限幅，留 headroom
- 用途：后续做多音效叠加、MIDI 合成、游戏音效时都要用这套防削波手法

### `i2s_diag2.py` —— 数据侧验证脚本（定位问题在软件还是硬件的利器）
- 原理：写入 1 秒（44100 帧）立体声数据，测 `write()` 阻塞耗时
- 结果判断：
  - 耗时 ≈ 900~1000ms → **DMA 按 44.1kHz 实时输出 → ESP32 侧正常，问题在 DAC 硬件**
  - 耗时 ≈ 0ms → 数据没按采样率送出去 → 查 ESP32 配置
- 实测：895ms → 确认 ESP32 侧正常

### `i2s_mix_test.py` —— 多音轨合成测试（✅ 已跑通）
- 功能：验证 I2S 输出"多声音重叠"的混合 PCM 能力
- 听感：单音 A4(440Hz) → 双音 A4+E5(纯五度) → 三音 A 大三和弦(440+554.37+659.25)
- 关键点：
  - **多轨叠加**：每个采样点把多个正弦值相加，再统一缩放 → 输出混合 PCM
  - 音量控制：每轨 VOL=0.28，三轨叠加峰值约 0.84，**不会削波**（溢出会破音）
  - 性能：用相位增量法（`phases[k] += steps[k]`），避免每样本重复乘法；
    用位运算 `s & 0xff / (s >> 8) & 0xff` 代替 `struct.pack`，生成更快
- 用途：这是 I2S 的基础测试，证明 DAC 能播混合音轨（如后续接 MIDI/多音合成器）

### `i2s_diag.py` —— 已废弃
- 用 `I2S.irq()` 回调计 DMA 帧数，在 ESP32 固件上回调不触发（frames=0），**不可靠，别用**

## 6. 无声问题排查全流程（本次实际走过的路）

1. 软件正常跑完但没声音 → 先用 `i2s_diag2.py` 验证 ESP32 侧数据输出
   （write() 耗时 895ms → **ESP32 侧 100% 正常，问题锁定 DAC 硬件侧**）
2. 检查 XSMT：**悬空是主因**，改为 GPIO12 软件拉高 → 有声 ✅
3. 备选检查项：SCK 悬空 → 改接 GND；GND 共地；供电；输出负载类型

## 7. 踩坑清单（快速回顾）

| 坑 | 解决 |
|---|---|
| 无声（XSMT 悬空） | XSMT 接 GPIO12 拉高，或直接接 3.3V |
| SCK 悬空电平不定 | SCK 接 GND，强制 PLL |
| MicroPython `to_bytes` 不支持 kwargs | 用 `struct.pack("<h", v)` |
| I2S.irq 回调不触发 | 用 `write()` 阻塞耗时验证 DMA |
| macOS pip PEP 668 / 版本 bug | 手动装 wheel 到用户 site-packages |
| `timeout` 命令不存在 | 去掉，脚本本身秒级完成 |
